[English](FDE-TOOLKIT.en.md) · [返回首页](../README.zh-CN.md) · [机器可读设计稿](toolkit-blueprint.json)

**目标：让 FDE 按“要完成的工作”选能力，并拿到可核对的交付物。**

当前是架构与首批候选方案，不是已发布的 Skill 包。不提供一键安装命令，不包含本地 Skill 正文、客户资料或私有系统连接器。入选不代表完成授权、兼容或行为验证。

## 从业务任务进入，不从工具名称进入

| 任务入口 | 用户真正遇到的问题 | 应交付什么 | 主要使用者 |
| --- | --- | --- | --- |
| 业务诊断 | 需求很大，却不知道第一步该做哪件事 | 问题定义、证据与假设、范围、基线和验收口径 | FDE、业务负责人、解决方案顾问 |
| 产品与营销 | 产品功能很多，却说不清谁为什么需要它 | 客群判断、价值主张、营销路径、内容或合作方案 | 营销 FDE、产品团队、增长团队 |
| 知识与数据 | 资料分散，口径冲突，回答无法回到证据 | 数据/知识清单、口径契约、来源映射、检索与核对样例 | 数据 FDE、知识工程师、服务团队 |
| Agent 工程 | 原型能跑，但工具、权限和状态没有说清 | 能力契约、接口、权限范围、异常与恢复设计 | Agent 工程师、交付工程师 |
| 评估验收 | 看起来不错，却无法判断什么时候能用 | 测试任务、分层失败分类、验收证据与待办 | FDE、质量负责人、业务验收人 |
| 交接复用 | 项目结束后，方法仍留在某个人的对话里 | 决策记录、操作手册、模板、故障处理与复盘 | 项目负责人、维护者、新加入团队的人 |

任务分类面向使用者；底层能力仍可按工程领域维护。一项 Skill 可以支持多个任务，不需要复制多份来增加目录数量。

## 四层组织：每一层卖点与责任不同

| 层 | 内容 | 用户价值 | 发布边界 |
| --- | --- | --- | --- |
| **方法核心** | 问题定义、交付契约、证据账本、验收与复盘模板 | 把“会用 AI”变成“能交付” | 先核实自研权属，再决定许可；不默认开源 |
| **场景配方** | 将若干 Skill 组成有输入、交接和验收的工作链 | 面向营销、客服、分析等任务，减少重新组织工作的成本 | 发布合成示例，不发布客户工作资料 |
| **能力适配** | 社区 Skill、平台连接器、工具与环境适配 | 复用专业能力，不重复造轮子 | 保留作者、来源、版本与许可证；优先索引上游 |
| **项目私有层** | 客户数据、本体、配置、凭据与专属业务规则 | 完成真实企业场景的最后一段适配 | 不进入公开工具包；按项目独立管理 |

这是一种产品化交付结构，而不是宣布已有四款成熟产品。Skill 给出方法，宿主 Agent 和工具负责执行；持久任务、并发、权限和故障恢复仍需运行时支持。

## 首批 8 个候选：先做小而完整的工作路径

以下名称来自已有能力清单，只用于定位和评审。没有复制其正文，也没有将社区能力标成自研。

| 候选能力 | 选它解决什么 | 第一份可核对产物 | 进入工具包前的重点 |
| --- | --- | --- | --- |
| `market-research` | 找清客群、市场假设与调研问题 | 带来源和假设的市场研究简报 | 核对来源和 MIT 声明；补齐有效描述；市场规模不能伪装成精确测量 |
| `competitive-analysis` | 把竞品资料转成产品差异判断 | 竞品对照与差异化假设 | 核对上游、日期与许可；不照搬竞品文案 |
| `kol-pitch-workflow` | 从“找红人”走到有理由的合作切口 | 候选筛选依据、个性化 pitch 与回复交接 | 去除私有系统耦合；确认权属；对外发送单独授权 |
| `product-capability` | 把产品想法转成实现前必须确认的约束 | 能力契约、接口和未决事项 | 验证缺失的模板引用；区分业务承诺与工程偏好 |
| `api-design` | 让分散的接口有一致的资源与错误语义 | API 契约与联调检查表 | 核实上游许可、版本兼容；文档不等于服务已部署 |
| `agent-eval` | 用同一任务比较编码 Agent | 任务集、通过率、成本、耗时和一致性记录 | 仅用于编码 Agent 比较，不代替业务 Agent 验收；确认 CLI 与隔离环境 |
| `architecture-decision-records` | 让下一位工程师理解为什么这样设计 | 决策记录与备选方案 | 核实上游；删除身份信息；避免默认扫描不在范围内的项目 |
| `sop-builder` | 让有经验的人能把流程交给别人 | 包含异常分支的操作手册 | 核实 MIT 声明；由实际操作人走读，不用“文档存在”代替可执行性 |

候选覆盖研究、营销、工程和交接，并不代表六类任务已完整覆盖。**知识检索质量、数据口径、业务动作安全与业务结果验收**，需要进一步遴选或原创补充，不能用一个通用 `agent-eval` 冒充解决。

## 三条最值得先跑通的配方

### 01 · 从产品资料到海外创作者合作草案

输入是经过授权的产品信息、目标受众和合作限制。先整理价值主张与可证明事实，再筛选创作者、解释匹配理由，最后写个性化 pitch 和回复处理清单。

验收看：每个推荐是否有来源；产品承诺是否有依据；提案是否针对对方内容；待确认商务条件是否明确。**草案生成不包含自动发信或承诺合作。**

### 02 · 从产品需求到可交接的 Agent 能力

输入是需求、现有接口和一个受控测试环境。先写能力契约和权限边界，再设计工具接口与状态处理，最后用固定任务比较实现，留下决策记录和运维手册。

验收看：输入输出是否清楚；写入和重试是否安全；失败能否定位；下一位工程师能否复现。自动执行、部署和生产权限不由 Skill 文本授予。

### 03 · 从客服资料到有依据的回复工作流

输入是获准使用的产品资料、服务规则和合成问题集。先对齐资料版本与口径，再建立检索、引用和回复修订流程，最后测试未知、冲突、过期和升级处理。

这一条是**下一阶段补齐方向**，不是已经存在的完整组合。验收需要检索与答复证据、服务边界和修订回流，不能只看文字流畅度。

## 每个条目必须记录什么

身份与权属：稳定 ID、名称、维护者、原作者、上游 URL、commit、许可证及其证据位置。没有核实的信息保持 `null` 或 `pending`，不补造来源。

使用条件：解决的问题、明确不解决的事、输入、输出、运行环境、依赖、权限、成本前提和是否涉及对外动作。

质量与维护：合成示例、行为测试、失败用例、最后验证日期、兼容版本、已知限制、更新策略和回滚方式。

## 从候选到可安装，经过五道门

1. **来源与许可**：明确自研、授权改编、可索引上游或暂不分发；有许可证文本也需核对适用范围和来源。
2. **内容与隐私**：排除客户、真实 Agent 身份、个人信息、凭据、内部域名与原始附件；保留必要的第三方署名。
3. **结构与依赖**：校验入口、完整资源、引用、语法与宿主工具；不能只复制 `SKILL.md`。
4. **行为与安全**：用合成任务测试正常、缺输入、权限不足和失败恢复；外部发送、部署、花费或写入须在授权范围内。
5. **小包发布**：先让一条配方与少量 Skill 真正跑通，记录版本、校验值与兼容环境，再扩大目录。

未来可为每个候选标注 `catalog-only`、`needs-adapter`、`runtime-tested`、`private-only` 等状态。当前设计稿所有条目均为 `candidate`，`installable: false`；不应让 Agent 根据此文件自动安装。

## 与现有站点的关系

服务站解释业务价值；案例集展示工作过程；学院训练交付方法；Toolkit 将经过验证的能力组织成可复用配方。首版适合独立仓库维护，在现有站点增加入口即可，不把几百个 Skill 代码混进静态营销网站。

下一步应先确认自研权属与分发方式，选一条最有代表性的配方，并在目标宿主环境完成实际测试。是否开源、采用什么许可、是否创建新仓库，均需由维护者明确决定。
